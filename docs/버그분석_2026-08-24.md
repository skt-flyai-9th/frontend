## 1. 유튜브 재생 오류 152

### 문제 코드 (v12)
| 위치 | 내용 |
|---|---|
| `src/ui/GuidePlayer.tsx` (v12 :371 부근) | `source={{ html, baseUrl: 'https://www.youtube.com' }}` — **문서가 유튜브인 척 위장** |
| `src/ui/guidePlayerHtml.ts` (v12, 삭제됨) | iframe API 로 플레이어 생성 — 위장된 origin 위에서 동작 |

### 원인
유튜브가 "youtube.com 이라고 주장하지만 실제로는 아닌" 문서의 임베드를 위장으로 판정 → 플레이어 자체 오류 **152**. v12 에서 `origin` 파라미터만 빼봤지만 baseUrl 위장 자체가 남아 있어 재발.

### 수정 (v13)
| 위치 | 내용 |
|---|---|
| `src/ui/guidePlayerBridge.ts` (신규) | **유튜브 embed 페이지를 WebView 최상위 문서로 직접 로드** — origin 이 *진짜* youtube.com. 위장 없음. 문서 안의 표준 `<video>` 요소를 직접 제어 (`:83~90` __cmd: play/pause/seek/rate/loop) |
| 같은 파일 `:72~80` | 유튜브 자체 오류 UI(.ytp-error)에서 **코드 숫자를 긁어 화면에 전달** — 또 막히면 화면의 숫자가 곧 진단 |
| `src/ui/GuidePlayer.tsx` | `source={{ uri: embedUrl }}` + `injectedJavaScript={GUIDE_PLAYER_BRIDGE}` 로 전환. iframe API·내장 HTML 경로 삭제 |

### 검증 (컨테이너, 실제 재생)
```
✅ ready (실제 video, 60s)   ✅ play→state:1   ✅ pause→state:2
✅ rate 0.5 이벤트 + 실측: 2초 동안 재생시간 +1.02s (0.5배 실증)
✅ seek(30)   ✅ 구간반복 43→40 되감김
✅ 실제 유튜브 오류 UI → err 코드로 수신 (차단 환경에서 확인)
```
재생 자체의 최종 확인은 실기기 APK 입니다. 이번 구조는 "폰에서 유튜브 embed 가 열리는 것"과 동일 조건입니다.

## 2. 촬영 무한반복 (간판 다시 찍기)

### 문제 코드 (v12)
| 위치 | 내용 |
|---|---|
| `src/api/upload.ts` — `mockUpload()` (v12 :55~66) | 업로드 완료 시 **가짜 응답만 만들어 반환** — `resolve({ taskStatus:'DONE', ... })` |

### 원인
Mock 서버(`src/api/mock/server.ts`)의 태스크 상태는 **한 번도 안 바뀜** → 업로드 "성공" 후 목록 재조회(`useUploadFootage` onSuccess invalidate, `src/api/queries/shoot.ts:99`)를 하면 같은 태스크가 여전히 미완료 → 다음 할 일로 또 간판. **"저장은 상태를 실제로 바꿔야 한다"는 프로젝트 제1규칙을 mock 업로드가 어긴 것.**
(제 이전 검증이 못 잡은 이유: 테스트가 서버 함수를 직접 호출해 이 우회 경로를 안 탔습니다. v12 의 "704 평가" 수정은 다른 지점이었고 이 버그는 그대로였습니다 — 제 오진입니다.)

### 수정 (v13)
| 위치 | 내용 |
|---|---|
| `src/api/upload.ts` `mockUpload` 완료부 | `mockRequest(API.taskFootage(taskId),'POST',…)` 를 **실제로 호출**해 서버 상태를 바꾸고 그 응답을 반환 (`.then(res => resolve(toCamel(res)))`) |

이후 흐름: 업로드 → mock 서버 태스크 DONE → invalidate → 목록에 반영 → 다음 태스크로 진행.

## 3. 영상 저장 실패

### 문제 코드 (v12)
| 위치 | 내용 |
|---|---|
| `src/lib/useSaveToGallery.ts` (v12 :34) | `MediaLibrary.requestPermissionsAsync()` — **읽기 권한까지 묶어서 요청** |
| 같은 파일 :57 | 실패 Alert 에 이유 없음 → "안 된다" 외 정보 0 |

### 원인
저장에는 읽기가 필요 없는데 기본 요청이 "사진·미디어 읽기"까지 물음. Android 13+ 에서 읽기를 거절하면 `granted=false` → 저장 경로 전체 차단. (`File.downloadFileAsync`·`MediaLibrary.Asset.create` 자체는 SDK 57 정식 API — `node_modules/expo-file-system/build/File.d.ts:40`, `expo-media-library/build/types/Asset.d.ts:193` 으로 확인.)

### 수정 (v13)
| 위치 | 내용 |
|---|---|
| `src/lib/useSaveToGallery.ts` | `requestPermissionsAsync(true)` — **writeOnly**. 부분 허용(limited)도 통과 |
| 같은 파일 catch | 실패 Alert 에 원인 메시지 80자 첨부 — 화면 문구가 곧 진단 |

> 참고: v12 에서 교체한 실재 URL(구글 샘플 mp4)은 유지됩니다. v11 이전의 "0초·저장불가" 1차 원인이 가짜 도메인이었고, 이번 건은 그 다음 겹(권한)입니다.
